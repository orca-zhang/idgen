# idgen 计数器缓存行优化（2026-11-19）

对比上一版本地“原子指针复用计数器”实现，当前版的不同实例 4/8 核并发调用摊销开销从 **7.219/11.360 ns/op** 降到 **0.581/0.342 ns/op**，约为原来的 **12.4/33.2 倍**速度。串行仍约 **2 ns/op**。复用生成器的三种场景均维持 **0 B/op、0 allocs/op**。

这里的并发 ns/op 是总耗时除以全部调用次数，不是单次请求延迟，也不是持续唯一 ID 产出能力。

## 最小改动

[具体 diff](idgen-padding.patch)只调整计数器的内存间距，并把分支内重复的 `now()` 写法合并到入口一次读取。缓存依赖升级到已公开的 ecache2 v0.1.1，x/sys 保持 v0.30.0，改为直接依赖。

```go
counter := struct {
    value [2]int64
    _     cpu.CacheLinePad
}{value: [2]int64{ts, -1}}
cache.Put(key, &counter.value)
```

缓存仍使用 `[2]int64{时间戳, 实例号}` 键；生成器仍持有指向 `[2]int64{时间戳, 序号}` 的原子指针。填充只发生在后台准备计数器时，不增加发号路径的操作。没有新增接口、clockState、历史 map 或计数器封装类型。

上一版的独立计数器只有 16 字节，Go 可能把不同实例的计数器放进同一条 128 字节缓存行；原子自增会使这些独立实例争用缓存行。隔离它们后，多个实例能够并行递增。缓存库的锁隔离无法单独解决这个问题，因为复用指针后的常用发号路径根本不访问缓存锁。

ID 位布局、实例号掩码、同实例共享序列、约一分钟回拨复用、clock 发布顺序和 Redis 命令逻辑保留。IDGen 使用后仍不能按值复制。

## 代价与边界

arm64 的填充是 128 字节，计数器对象的逻辑大小从 16 变为 144 字节，实际堆分配还受分配器大小类影响。正常每秒准备 16 个实例，新增逻辑空间约 2 KiB/秒；缓存最多保留 4096 个条目时，填充约占额外 512 KiB。它不是每次发号的分配成本。未测完整业务吞吐或其他架构的性能。

同实例的共享序号仍需要原子递增，真实争用依然存在。18 位每秒序号容量与原有溢出行为保留；基准会超过这一容量，因此只衡量调用开销。
